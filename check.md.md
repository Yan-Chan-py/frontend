**Мета етапу**  
Реалізувати серверну частину Flora: Express-застосунок з коректною архітектурою, підключений до хмарної PostgreSQL через Sequelize, з повним REST API для колекції bouquets (CRUD \+ Joi-валідація), можливістю завантаження зображень через Multer, задокументований Swagger, задеплоєний на хостинг. На виході — full-stack проєкт з працюючим клієнт-серверним звʼязком, готовий до портфоліо.

**Що має бути реалізовано в проєкті на даний момент**  
(6 тематичних блоків)

* **Блок 1\. Архітектура та розгортання backend (Заняття 21–22)**

Структура проєкту логічно розділена на шари: запуск застосунку, маршрути, контролери, сервіси, middleware, схеми валідації, helpers/configs або їх аналоги. Точка запуску server.js / index.js. Підключені middleware для JSON, CORS, централізований обробник помилок. Файл .env з портом та іншими параметрами. Сервер запускається без помилок на актуальній LTS-версії Node.

* **Блок 2\. База даних PostgreSQL \+ Sequelize (Заняття 23–24)**

Створений акаунт на Render (або аналог), розгорнута хмарна база. Підключена через Sequelize з обробкою помилки (process.exit(1) при фейлі \+ повідомлення в console). При успіху — "Database connection successful". Модель Bouquet має поля, узгоджені з REST API, Joi-схемами та Swagger: photoURL або photo — обрати одну назву й використовувати її всюди, title, description, price, favorite / favourite — також обрати один варіант написання. Усі CRUD-операції перенесені з файлового зберігання на Sequelize-методи.

* **Блок 3\. REST API з валідацією (Заняття 25–26)**

Повний CRUD для колекції bouquets — розділений на шари controllers/services/schemas:

| Метод | Endpoint | Логіка |
| :---- | :---- | :---- |
| GET | /api/bouquets | Список усіх, 200 |
| GET | /api/bouquets/:id | Один за id, 200 або {message: "Not found"} 404 |
| POST | /api/bouquets | Joi-валідація обовʼязкових полів, 201 або 400 |
| PUT | /api/bouquets/:id | Оновлення переданих полів відповідно до логіки, розглянутої на занятті; якщо body порожнє — 400\. |
| DELETE | /api/bouquets/:id | Видалення, 200 або 404 |
| PATCH | /api/bouquets/:id/favorite | Оновлення статусу favorite |

Валідація через Joi-схеми в окремих файлах. Централізована обробка помилок (HttpError.js). Якщо validateBody.js / HttpError.js helper'и не використовуються — видалені з проєкту.

* **Блок 4\. Робота з файлами та зображеннями (Заняття 27–28)**

Підключений Multer. Створені папки /temp (для тимчасових файлів) і /public/photos (для постійних). Express налаштований на роздачу статики з /public. При створенні букета генерується URL через gravatar і зберігається в photoURL. PATCH-ендпоінт для оновлення фото: приймає multipart/form-data, перекладає файл з /temp у /public/photos з унікальним імʼям, повертає 200 з новим URL. Обробка помилок реалізована відповідно до логіки проєкту: 400 при відсутньому або некоректному файлі; 401 — лише якщо в проєкті реалізована авторизація для цього endpoint. Усі назви, пов’язані із зображенням, мають бути уніфіковані: photoURL у Sequelize-моделі, Joi-схемах, Swagger і відповіді API. Не використовувати avatarURL, якщо endpoint працює із фото букета.

* **Блок 5\. Документація Swaggerswagger.json (або openapi.json) з розділами paths та components → schemas. (Заняття 29–30)**

Окремі схеми для повного обʼєкта (Bouquet), створення (BouquetCreate — без серверних полів), оновлення (BouquetUpdate — без required). Використання через $ref.  
**Критична вимога:** Swagger-схеми синхронізовані з Joi-валідацією та Sequelize-моделями (однакові назви полів, однакові типи, однакові обовʼязкові поля в create-схемі). Swagger UI доступний за URL і коректно відображає всі ендпоінти.

Swagger має описувати саме ті endpoint-и, які реально реалізовані в backend. Не залишати приклади з іншого проєкту або старі назви ресурсів.

* **Блок 6\. Фінальна інтеграція та деплой**

Frontend перемкнений з json-server на реальний backend. Backend задеплоєний на хостингу (Render або аналог), доступний за публічним URL, стабільно працює. Фінальний PR створений і поданий на код-рев’ю; якщо рев’ю вже проведено — фідбек врахований, PR змержений у main. Фінальна версія frontend задеплоєна на GitHub Pages і працює зі справжнім API. README.md з інструкцією запуску локально (опціонально, але вітається).  
**Критерії прийняття (обовʼязковий мінімум)**

* Backend запускається локально без помилок.  
* Підключення до PostgreSQL стабільне.  
* Усі REST-ендпоінти відповідають (перевіряється через Postman/Swagger UI).  
* Joi-валідація працює (некоректне body → 400 зі змістовним message).  
* Swagger UI доступний, і схеми узгоджені з реальним API.  
* Backend задеплоєний на хостингу і доступний за публічним URL.  
* Frontend працює з реальним backend.  
* Проведено код-рев'ю ментором або викладачем.

**Типові помилки студентів﻿**

* Одна Swagger-схема на всі запити — id у create, required у update.  
* Назви полів у Swagger не співпадають з контролером (наприклад, avatarURL у доці vs photoURL у коді).  
* Joi-валідація в контролері замість окремого middleware — код дублюється між POST і PUT.  
* Не обробляють помилку підключення до БД → сервер «падає мовчки».  
* Зберігають завантажені файли одразу в /public без проміжного /temp — ризик залишити «сміття» при фейлі обробки.  
* Backend задеплоєний, але frontend все ще ходить у json-server → демо «на демо».  
* process.exit(1) забутий при фейлі підключення — сервер запускається, але падає при першому запиті.  
* Не видаляють HttpError.js / validateBody.js якщо їх не використовують.
